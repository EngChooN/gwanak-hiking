# 카메라 지형 광선 검사 최적화 — 실행 검증 대기

산개발 / 2026-11-03. 커밋·push·삭제 없음.

## 근거와 원인 범위

산기획 검수 기록과 `artifacts/visual-fix-verify-2026-11-03/performance-after4-visual-fix/balanced-4x-third-w.cpuprofile`을 확인했다. 이 기록의 39.7fps·최대 2,283ms는 수정 전 수치이며 이번 수정 결과가 아니다.

프로파일의 getVertexPosition 노드 24(1,279회 샘플)의 상위 호출은 qr → _computeIntersections → raycast → intersectObjects → Ib(번들 4148행)다. 현재 소스의 매 프레임 카메라 충돌 검사는 중앙·근평면 모서리 5개 광선을 발사한다. XZ 상자로 청크를 고르지만, 선택한 각 청크 안에서는 모든 삼각형을 검사한다. 계단 주변 지형을 낮춘 후에도 메시 단위 경계 상자가 넓어 이러한 전수 검사가 남는다.

발 접지 surfaceHeight는 기존 surfaceIndex의 삼각형 높이 색인을 사용한다. groundCheck의 전체 지형 광선 검사는 캡처 요청 때만 호출한다. terrain-clearance는 청크 생성 및 초기 상시 지형 생성 때 실행한다. 따라서 반복 광선 순회의 우선 개선 대상으로 카메라 경로를 선택했다. 계단 변경이 어떤 경계 상자를 얼마나 넓혔는지, 2,283ms 프레임이 어느 작업 때문인지는 아직 확정하지 않았다. 생성·셰이더 준비 등 별도 원인이 남아 있을 수 있다.

## 수정

- `src/static-raycast.js`: 정적 indexed 단일 재질 메시의 삼각형을 중심 좌표 기준 8m 칸에 한 번 배정한다. 각 칸 AABB는 실제 세 꼭짓점을 모두 포함하므로 칸을 넘는 삼각형도 빠지지 않는다. 광선을 로컬 좌표로 변환해 겹치는 칸만 Three.js 기본 Mesh.raycast에 전달한다. 원래 faceIndex·object·uv·앞뒷면·near/far 판정을 보존한다.
- `assets/realistic/load-landscape.js`: 등산로 생성 직후와 청크의 계단 여유 처리 직후 색인을 만든다. 렌더링 버퍼와 지형·계단 높이는 바꾸지 않는다. 보조 메시는 장면에 추가하지 않으며 GPU에 제출하지 않는다. 청크 참조가 해제되면 보조 색인도 함께 GC 대상이 된다.
- `tests/static-raycast.test.mjs`: 변환·칸 경계·사선·near/far 교차 일치, 계단과 여유 처리 지형의 수직·수평 광선 일치, 64m 청크의 짧은 광선 꼭짓점 조회량 90% 이상 감소를 검사하는 3개 테스트를 작성했다. 미실행이다.
- `scripts/benchmark-performance.mjs`: 균형 최소 fps를 30에서 50으로 올리고 독립 rAF와 실제 렌더 지표 모두 최대 500ms를 요구한다. 높음 최소 55fps는 유지한다. maxFramePass·maxFrameBudgetMs를 결과 JSON에 기록한다.

## 정적 확인 및 한계

`git diff --check` 통과. Three.js 로컬 Mesh.raycast 구현을 읽어 보조 메시에 공유하는 position·normal·uv 속성과 교차 결과 복구를 검토했다. 새 구현은 위치·인덱스가 설치 이후 변하지 않는 정적 메시 전용이다. geometry 교체는 원래 raycast로 되돌아가며, 동일 geometry 내부 변형에는 색인 재생성이 필요하다. 현재 적용 위치에서는 계단 여유 처리가 끝난 뒤 색인을 설치한다.

완료 기준인 균형 CPU 4배 50fps 이상, 최대 프레임 500ms 이하, 높음 수준 유지, 전체 테스트 통과, 계단 접지 오차 3cm 이하는 모두 실행 검증 대기다. 구현만으로 달성을 선언하지 않는다.
