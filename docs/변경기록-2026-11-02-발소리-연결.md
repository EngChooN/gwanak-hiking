# 발소리 재생 연결 — 산개발

기준: design/발소리-소리목록.md 및 ‘발소리 재생 연결 (계단 먼저)’ 업무 카드.

## 결과

src/footstep-audio.js를 추가하고 기존 hiking:step에 연결했다. 소리 전용 걸음 타이머는 없다. strideFor 거리 누적 때 발생한 걸음마다 한 번 재생한다. 계단은 기존 공칭 한 걸음(약 0.349857m)·초당 1.2걸음을 유지한다.

- 계단: stairs=돌 6개, deck_stairs=통나무 7개.
- 기타: soil=흙 9, rock=돌길 8, deck=평탄 데크 3, ridge=암릉 2.
- public/sounds/에 35개 동일 바이트 복사. design 원본 보존. 장시간 나무 계단 원본 클립은 게임에 복사하지 않고 가공된 13개만 사용.
- 계단은 직전 2개, 기타는 직전 1개 파일을 제외하는 재질별 순환 주머니. 전부 사용한 뒤 다시 무작위 순환한다.
- 음높이 ±4%·음량 ±1.5dB·좌우 팬 ±0.08. 3인칭 -3dB, 경사 10% 이상 +1dB·저역 +1.5dB. 합산 후 -6dBFS 이하 소프트 리미터·짧은 꼬리 페이드.
- 첫 포인터/키 입력에 AudioContext 생성·시작. 헤더 ♪ 토글과 별도 소리 설정 저장. 일시정지·화면 이탈·끄기에 현재 소리도 짧게 페이드해 중단.
- 이동 이벤트의 재질을 프레임 시작 위치에서 실제 접지 위치로 교정했다. elapsed·s·slope를 진단 데이터에 추가했다.
- 콘솔 [발소리] / window.hiking.audio() / ?audioDebug=1에서 변형·재질·시간·음높이·음량·팬 확인.
- 조작 안내 > 소리 출처와 public/sounds/CREDITS.md에 CC0 및 암릉 CC BY 3.0 출처·변경 내용 표시.

## 검증

Node v22.17.1. npm test 25개·npm run build 통과. 추가 5개는 112단×1000회 직전 2개 제외와 사용률, 모든 재질·변형 범위·팬, 원본 바이트 대조, 실제 계단 이벤트 간격, 접지 재질 경계를 검사한다.

BASE_URL=http://127.0.0.1:4173 node scripts/capture-audio.mjs 통과. 첫 입력 전 AudioContext 없음, 첫 R 입력 후 35개 디코딩 및 Analyser 출력 신호 확인. 실제 계단 12걸음=12회, 이동 이벤트 약 0.833333초·실제 오디오 시작 약 0.833초. 준비 중 누락 0. 돌 6·통나무 7 모두 사용, 직전 두 변형 반복 없음. 6재질 즉시 변경·3인칭·음소거·저장 복구·이탈 중단·360px 헤더 검사도 통과.

기존 npm run capture도 최종 빌드에서 통과: 10개 화면, 이동·시점·GPX·접지·Neutral/ACES 룩 회귀 유지. artifacts/audio-verification.json 및 browser-verification.json에 같은 dist/index.html SHA-256 기록.

artifacts/발소리-검증-보고.html에 실제 계단 화면·변형 번호/시간 로그·13개 원본 가공본 미리 듣기를 넣었다. 종합 구현-검증-보고.html도 갱신했다. 귀 검수 통과라는 주장은 하지 않는다.

## 가정

현재 GPX에는 deck_stairs가 없어 통나무 7개는 동일 공개 걸음 이벤트에 재질을 넣는 하네스로 확인했다. 실제 경로에 통나무 계단을 추가하지 않았다. 한 단은 기존 strideFor의 공칭 계단 걸음 단위를 따른다. 준비 전 걸음은 나중에 몰아서 재생하지 않는다. 데크 3·암릉 2개는 확보된 변형 수이며 설계 목표보다 적다.
