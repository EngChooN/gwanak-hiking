**읽는 법**
- 높음 화질은 60fps(화면 주사율 상한)에서 안정적이다. 끊김(50ms 초과)은 D키 구간에서 1번(66.6ms)뿐이다.
- 벤치마크 자체의 합격 판정은 높음 전 구간이 "미달"이다. 이유는 **삼각형 예산 250만 초과**(2.57~2.97M) 하나뿐이다. 프레임·컴파일·셰이더 항목은 모두 통과다.
- 균형·CPU 4배는 51fps이고 프레임이 33.4ms 격자에 붙어 있다. 4배 감속에서도 50ms 넘는 프레임은 없다. 벤치마크 기준(균형 50fps)은 넘지만 여유가 작다.
- 헤드리스 크롬의 GPU 표시는 "WebKit WebGL"이다. 실제 GPU 시간은 이 측정으로 직접 알 수 없다. 높음 화질에서 메인 스레드는 15초 중 약 9초가 idle이라 **CPU는 남고, 병목은 GPU 쪽 삼각형·픽셀일 가능성이 크다**(추정).
- 이번 측정은 M 시리즈 Mac 한 대뿐이다. 약한 GPU·모바일에서는 결과가 다를 수 있어 별도 측정이 필요하다.

## 2. 이미 적용돼 있는 것 (다시 할 필요 없음)

코드를 확인한 결과다.

- 동적 해상도·그림자 거리: `src/adaptive-quality.js`. DPR 0.8~1.6에 단계별 0.7~1 곱, 그림자 30~60m, AO 끄기를 프레임 시간으로 조정한다.
- 셰이더 사전 컴파일: `rendering.js`에서 `compileAsync` 사용. 첫 로딩 단계에서 이미 줄였다(산개발 4/4단계 1 결과).

- 지형 청크 스트리밍: 200m 청크 + 프레임당 1개 attach.


합격 조건: 프레임·50ms 초과 수가 기준값보다 나빠지지 않을 것, 삼각형 평균이 줄 것, `npm test` 전부 통과. 같은 위치·시각에서 전후 캡처를 비교한다(`scripts/capture.mjs` 또는 벤치마크가 남기는 `*-w.png`).

### 4-1. 풀밭 거리 LOD (`src/toon/grass-field.js`, `src/toon/nature.js`)

1. `nature.js`의 `grassGeometries.field`(17잎) 옆에 `fieldFar`를 하나 더 만든다. `grassClump({blades:8,height:.58,spread:.42,flowers:1,seed:21},palette)`처럼 잎만 절반 정도로 줄이고 키·퍼짐은 같게 둔다. 같은 `seed`라 앞쪽 잎 배치가 겹쳐 모양이 비슷하다. `geometries.grass.fieldFar`로 내보낸다.
2. `createGrassField`가 `InstancedMesh`를 둘 만든다. 근거리 `mesh`(기존)와 원거리 `meshFar`(같은 재질, `fieldFar` 지오메트리). 둘 다 `frustumCulled=false`, `receiveShadow=true`, `castShadow=false`, `userData.metricKind='하층 식생'`, `toonGroundCover='field'`를 똑같이 단다(벤치마크 분류와 `swapGroundCover`가 쓰는 이름이므로 동일하게).
3. `update()`에서 다발마다 `dx²+dz²`를 이미 계산하므로, 경계 거리 `nearR`(제안: 반경 `R`의 0.45배) 안이면 `mesh`, 밖이면 `meshFar`에 행렬을 쓴다. 각각 `count`와 `instanceMatrix.needsUpdate`를 갱신한다. 상한 `capacity`는 둘을 합쳐 지킨다(가까운 쪽이 먼저 차도록 현재의 가까운 타일부터 채우는 순서를 유지).
4. 경계에서 잎 수가 확 바뀌어 보이지 않게, 셰이더의 `tgFieldRadius` 페이드는 그대로 두고 `nearR` 근처에 두 메시의 겹침 구간(약 2m)을 둔다. 그 구간에서 먼 쪽 다발의 일부(해시로 절반)만 그린다.
5. `status`에 `clumpsNear`, `clumpsFar`를 추가하고 `dispose()`에서 둘 다 `scene.remove`·`dispose`한다.
6. 테스트: `tests/`의 풀밭 관련 테스트가 있으면 인스턴스 수가 `capacity` 이하인지, 두 메시 합이 기존 `status.clumps`와 같은지 확인한다. 없으면 `GRASS_FIELD`를 읽는 작은 단위 테스트를 추가한다.
7. 위험과 대처: 경계가 눈에 띄면 `nearR`를 키우거나 `fieldFar` 잎 수를 10~11로 올린다. 새 지오메트리 때문에 셰이더 변형이 늘지는 않는다(재질이 같다). `compilePass`(컴파일 수 변화 0)가 유지되는지 벤치마크로 확인한다.

### 4-2. 길가·숲 바닥 풀 밀도 곡선을 연속화 (`assets/realistic/near-detail.js:89`)

현재 `updateGroundCover`는 거리 `near`(10/16/24m) 안이면 밀도 100%, 밖이면 35%, `far`(28/45/65m) 밖이면 숨긴다. 이 청크 단위 계단이 먼 곳 풀을 필요 이상으로 많이 그리게 한다.
1. 밀도를 거리에 대한 연속 함수로 바꾼다. 예: `t=clamp((distance-near)/(far-near),0,1)`, `density=base*(1-0.8*t)`. 즉 `near`에서 100%, `far`에서 20%로 줄인다. `Math.ceil(fullCount*density)`는 그대로 둔다(고정 난수 순서의 앞부분만 쓰는 방식이라 풀이 미끄러지지 않는다).
2. `count`가 프레임마다 조금씩 바뀌어도 `instanceMatrix` 재업로드는 없다(앞쪽만 그림). 단, 값이 매 프레임 흔들려 풀이 깜빡이지 않게 `density`를 0.05 단위로 양자화한다.
3. 기존 테스트가 이 함수의 값(예: 35%)을 검사하면 새 곡선 기준으로 고친다(`grep -rn updateGroundCover tests`).
4. 효과가 4-1에 비해 작을 수 있어, 4-1 먼저 재고 필요할 때 적용해도 된다.

### 4-3. 컬링 재계산 빈도 낮추기 (`assets/realistic/load-landscape.js:359-405`)

1. `update(camera)` 앞쪽에 카메라 변화 판정을 만든다. 마지막으로 계산했을 때의 `camera.position`과 `camera.quaternion`, `camera.zoom`을 저장해 두고, 위치 변화가 0.25m 미만이고 방향 변화(`angleTo`)가 0.3° 미만이고 `quality`·`zoom`이 같고 마지막 계산 뒤 4프레임이 안 지났으면 **지형 청크 가시성(`culler.visible` 루프)과 숲 버킷 순회를 건너뛴다**.
2. 건너뛰는 동안 `mesh.visible`·`lod.visible`은 이전 값이 그대로 남으므로 동작이 같다. 청크가 새로 붙거나 떼질 때(`terrainStream`·`vegetationStream` 상태 변화)는 반드시 즉시 다시 계산한다. `status`가 바뀌는 시점에 `dirty=true`를 세우는 방식이 안전하다.
3. `foliageUniforms`·`nearTrees.update`·시설 `update`는 건드리지 않는다(바람·근경 나무 전환은 매 프레임 필요).
4. 5프레임(약 83ms)보다 오래 건너뛰지 않는다. 최대 지연을 두면 갑작스러운 회전에도 팝이 거의 없다.
5. 테스트: 카메라를 0.1m 움직이는 경우 두 번째 `update`가 순회를 건너뛰고(`status`의 새 카운터), 청크가 추가되면 즉시 다시 순회하는지 확인한다.
6. 측정: 4배 감속 프로파일에서 `visible`(chunk-culling.js:37)과 `landscape.update` 시간이 줄었는지 비교한다.

## 5. 가정

- 효과 퍼센트는 코드 읽기와 이번 측정을 바탕으로 한 추정이다. 풀밭 다발 삼각형(약 95개 × 7,200)은 잎 17개 × 5삼각형 + 꽃을 어림한 값이며 실측하지 않았다.
- 측정은 헤드리스 크롬·M 시리즈 Mac 한 대·DPR 1이다. 실제 GPU 시간과 약한 기기 결과는 별도로 재야 한다.
- 조사는 아래 출처의 공식 문서와 토론 글을 기준으로 했다. 페이지 전문을 직접 받아 읽지는 않았고 검색 결과의 요약 근거라서, 적용 전에 해당 문서의 현재 버전(three 0.180)을 한 번 더 확인해야 한다.
- 서버는 `vite` 개발 서버(5176)로 측정했다. 개발 서버는 번들·압축이 없어 로딩 시간은 비교 대상이 아니다. 프레임 측정에는 영향이 작다.
