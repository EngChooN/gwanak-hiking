# 이동·스테미너·휴식 통합 규약

2026-11-03 · 산개발

## 구현

- `speedFor`가 기존 결과의 1.2배. 계단·자동 걷기도 동일. 전체 ETA 125분(기존 150분).
- 입력 `run`(좌우 Shift)은 걷기의 1.6배. 길 밖은 다시 0.7배.
- 스테미너 0~100. 달리기 초당 `10 × (1 + 양의 실제 이동 경사)` 소모. 걷기 +4/s, 정지·충돌 +8/s, 앉기·차 동작 +15/s. 차 3초 완료 시 +30 한 번.
- 고갈 잠금은 30 이상에서 해제. 일시정지는 회복·차 시간을 멈춤.
- C: 앉기/일어나기. T: 앉아 있을 때만 차 시작. 이동 입력이나 자동 걷기 명령은 일어서며 차를 취소.
- `state.pose`는 `stand | sit | tea`, `teaRemaining`은 남은 초. `stamina`, `runExhausted`와 함께 저장·복원. 오래된 저장에는 기본값 적용.
- 길 밖 최대 좌우 `width / 2 + 8m`. 저장값이 최대 범위를 벗어나면 길 안 가장자리로 복귀. 유효한 길 밖 저장 위치는 유지.
- 길 밖 지면은 실제 clearance 적용 렌더링 삼각형. 35° 초과 경사·급단차와 큰 바위의 월드 경계 + 몸 반경 20cm에서 이동 차단. 바위 AABB를 사용해 모서리 부근은 보수적으로 막을 수 있음.
- 자동 걷기는 진행하며 중앙으로 복귀. 위험한 지형에서는 충돌을 무시하고 복귀시키지 않음.
- 코스 꺾임의 좌우 기준 방향은 전후 2m 중심선을 이용해 연속화. 길 밖 발소리는 기존 흙·낙엽 음원 뱅크 사용.
- 길 위 이동 거리 계산은 경로의 연속 고도. 계단의 시각적 단차는 발 접지·카메라 높이에 적용해 작은 프레임 거리 예산이 디딤판 상승을 막지 않게 함.

## 산풍경 연결

`main.js`는 `hiker.update`에 기존 인수와 함께 다음 값을 매 프레임 전달한다.

```js
{ pose, teaProgress, running, speed, dt, surfaceHeight }
// teaProgress: 0~1, surfaceHeight(x,z): 현재 길 안/밖 지면 높이
```

`hiker.ground`에도 `pose`와 길 밖 높이 조회 함수를 전달한다. 산풍경의 `realistic-hiker.js`가 자세·차 진행률·달리기·지면 입력을 처리한다. `update` 다음 `ground` 순서를 유지한다. 1인칭은 `floorHeight + hiker.eyeHeight`, 3인칭 주시점도 같은 높이 보간을 따른다. 일시정지 중 동작 dt는 0이며 저장된 앉기·차 자세는 시작 전에 복원한다.

## 산디자인 연결

`window`의 `hiking:state` 이벤트가 약 150ms마다 상태 복사본과 `speed`, `offTrail`을 전달한다. UI에서 `stamina`, `runExhausted`, `pose`, `teaRemaining`을 읽는다. 초기값은 준비 이후 `window.hiking.snapshot()`으로 조회할 수 있다. 이벤트의 `teaReady`는 앉기 전환 완료 여부를 포함한다. T 및 차 명령은 이 값이 참일 때만 시작한다. `src/rest-ui.js`는 명령 이벤트만 사용하며 C/T 버튼과 스테미너를 표시한다. 기존 `#sit` 버튼이 있으면 별도 패널을 만들지 않는다.

```js
window.addEventListener('hiking:state', ({detail}) => updateUI(detail));
window.dispatchEvent(new CustomEvent('hiking:command', {detail:{id:'sit'}}));
// id: sit | tea | auto | pause | view
```

초기 HTML에 `#sit`, `#tea` 버튼이 있으면 main.js가 클릭을 연결한다. 이 방식과 위 명령 이벤트 중 하나만 사용해 중복 명령을 피한다. UI는 차 버튼을 앉을 때만 표시하고 스테미너가 가득 차면 흐리게 처리한다.

현재 `weather.js`, `daytime.js`, 휴식 버튼·스테미너 UI의 내보내기 모듈이 없다. 실제 시간·날씨·바람·비 소리의 main 연결과 비·눈 성능 측정은 해당 모듈 제공 후 진행해야 한다. 해당 담당 파일은 수정하지 않았다.

## 로딩 단계 신호 (2026-11-03 추가 · 산개발 → 산디자인 로딩 화면)

로딩 화면 UI는 산디자인이 만든다. `main.js`는 아래 이벤트만 보내고 받는다. 진행률은 실제 await 지점에서만 오른다(시간 기반 자동 증가 없음). 구현은 `src/loading.js`.

```js
// main → UI. 같은 단계 안 0.5%p 미만 변화는 묶어서 보낸다. progress는 줄지 않는다.
window.addEventListener('hiking:loading', ({detail}) => {
  // detail = {stage, progress, label, stages, elapsedMs, ...}
  // stage: 'terrain'|'nature'|'facilities'|'hikers'|'environment'|'stabilizing'  (진행 중, 아직 끝나지 않은 첫 단계)
  //        'ready'   준비 완료(progress 1, loadMs, readiness)
  //        'started' 시작됨(입력·시간·자동 걷기 허용)
  //        'error'   실패(error 문구, failedStage, 마지막 progress)
  // label 예: '숲·바위 준비 중'. stages = {terrain:0~1, nature:0~1, ...} 단계별 실제 비율
});
// UI → main. '출발하기' 버튼(소리 재생 허용 겸용)에서 보낸다.
window.dispatchEvent(new CustomEvent('hiking:start'));   // 또는 window.hiking.start()
window.addEventListener('hiking:started', ({detail}) => {/* detail.position = {zone,x,z,heading,s,lateral} */});
```

| stage | 라벨 | 가중치 | 실제 진행 근거 |
|---|---|---|---|
| terrain | 지형 | 0.30 | `loadLandscape` 완료 0.6 → 첫 `terrain.update` 0.8 → `streamFar` 0.9 → `streamWater` 1 |
| nature | 숲·바위 | 0.30 | `loadOptionalModels`가 인스턴스를 만든 항목 수 / 전체 항목 수(×0.95), 접촉 음영까지 끝나면 1 |
| facilities | 시설 | 0.08 | 광장 시설(일주문·정자 등 `landscape.status.entrance`) 확인 |
| hikers | 등산객 | 0.10 | 등산객 GLB 로드 |
| environment | 날씨·환경 | 0.14 | 시각·날씨 환경 준비 0.3 → 도시 원경 청크 수 비율(0.3~0.9) → 1 |
| stabilizing | 첫 프레임 안정 | 0.08 | 셰이더 컴파일이 끝나고 프레임 간격 100ms 이하가 12번 연속(연속 수/12) |

- **준비 완료 조건**: 출발점 반경 60m(12방향×5거리) 지형·노면 높이가 모두 있음, 가까운 LOD(숲·바위 `natureReady`), 광장 시설, 등산객이 장면에 있음, 안정 프레임 12개. 하나라도 빠지면 `error`. 안정 프레임이 15초 안에 안 모이면 느린 기기로 보고 `readiness.stableTimeout:true`로 진행한다.
- **시작 방식**: 기본은 준비 완료 즉시 자동 시작. 로딩 UI가 '출발하기' 버튼을 쓰려면 `<html data-start-mode="manual">`(또는 주소 `?startMode=manual`)을 두고 버튼에서 `hiking:start`를 보낸다.
- **시작 전 차단**: 키·버튼 명령, 이동, 걸은 시간, 자동 걷기, 저장이 모두 멈춘다. 로딩 중 눌린 키는 시작 순간 버린다. 걸은 시간은 0초에서 시작한다.
- **실패·지연**: 로딩 중 예외·Promise 거부는 `error`로 바뀐다. 다시 시도는 `location.reload()`. 이 맥 headless Chrome에서 로딩은 약 36~37초(실측, 아래 변경 기록)라, 30초 안내는 **마지막 진행 신호 이후 경과**로 재는 것을 권한다(처음부터 30초로 재면 정상 로딩도 실패 안내가 뜬다).
- **검증 스크립트**: `await page.evaluate(()=>window.hiking.ready())` 로 준비 완료를 기다리고, 수동 시작 모드면 `hiking.start()`를 부른다. 자동 시작이면 `waitForFunction(()=>window.hiking?.started)`. `window.hiking`은 로딩 시작부터 `{started, ready, start, loading}`만 있고 나머지 진단 함수는 첫 프레임 전에 붙는다.

## 광장 출발과 위치 (2026-11-03 추가)

- `zone:'plaza'|'route'`. 광장은 경로에 묶이지 않는 자유이동(x, z, heading), 코스는 기존 (s, lateral).
- 광장 경계: `docs/입구광장-배치조사.md` §2 다각형(B, 문에서 8~38m·폭 12m)에 문까지의 접근부(기둥 안쪽 ±2.49m)를 이은 볼록 다각형(`src/plaza.js` `plazaPolygon`, 약 433㎡). 몸 반경 0.25m만큼 안쪽에서 막는다. 일주문 기둥·바리케이드 충돌은 기존 상수를 그대로 쓴다.
- 일주문 아래가 코스 시작 `GATE_S`(B 가설에서 GPX 0m 기준 −26.1m, A 가설이면 0). 내부 `s`는 저장 호환을 위해 GPX 0m 기준 그대로이고, 화면 거리는 `courseDistance = s − GATE_S`(일주문 0m)다. 광장에서는 0m, "출발 전 · 광장"으로 표시한다.
- 전환: 광장에서 통로를 지나 문 선분 좌표의 `s ≥ GATE_S`가 되면 코스로, 코스에서 `s < GATE_S`가 되면 광장으로. 위치는 같은 점으로 이어지고 카메라 방향은 `look.yaw`로 보존한다(실측: 전환 프레임 이동 2~6cm, 방향 변화 0°).
- 광장 조작: W/S는 시선 방향 앞뒤, A/D는 옆. 드래그로 시선을 돌린 뒤 걸으면 그 방향이 이동 기준(`plaza.heading`)이 된다. 자동 걷기는 통로 가운데(문 기준 x=+0.115m) 앞 1.2m로 간 뒤 문을 지나 코스를 계속 간다.
- 주소: `?start=entrance`(광장, 저장보다 우선), `?start=gate`(일주문 아래 s=GATE_S), `?start=demo`(545m 구간, 빈 프로필 캡처 스크립트용). 저장이 없는 첫 실행은 광장.
- 저장: 기존 키·`version:1`에 `zone`, `plaza:{x,z,heading}`를 더했다. 예전 형식(zone 없음)은 s<GATE_S면 그 월드 위치의 광장으로, 아니면 코스로 복원한다. 다른 일주문 가설에서 저장한 광장 위치는 새 출발.
- 멀티 대비 위치 함수(멀티 기능 없음): `playerPosition(state)` → `{zone,x,z,heading,s,lateral}`(광장에서 s·lateral은 null), `setPlayerPosition(state,pos)`(경계 밖 광장 좌표는 거부). 브라우저에서는 `window.hiking.position()`.
- `hiking:state`에 `zone`, `courseDistance`, `courseLength`, `position`, `started`가 추가됐다.
