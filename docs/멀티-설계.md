# 함께 걷기(멀티) 설계 · 내 컴퓨터 시제품 결과

작성: 산개발 · 2026-11-04 · 상태: 대표 결정 대기(서버는 올리지 않았습니다)

## 한눈에 보기
- **시제품은 되었습니다.** 같은 브라우저의 창 2개(`?multi=방이름`)에서 서로의 등산객이 보이고, 걷는 동작이 맞고, 이름표·인사·손 흔들기·같이 셀카가 동작합니다. 서버 없이 `BroadcastChannel`로 연결합니다.
- **다인원 성능:** 20명이 한곳에 몰려도 모델은 가까운 4명만 그리는 규칙에서 60Hz 안팎을 유지했습니다(헤드리스 크롬 CPU 측정). 20명 전원을 모델로 그리면 34fps로 떨어집니다.
- **서버 추천:** 1차 공개는 **직접 만드는 WebSocket 서버 1대(방 20명 제한)** 입니다. 유지비가 가장 낮고, 방식 전환 비용도 낮습니다(전송 계층만 갈아 끼우면 됩니다). 아래 비교와 결정 요청 참고.

## ① 서버 방식 비교

### 전제 (측정·계산 기준)
- 위치 메시지 10회/초. 메시지는 압축 시 **15바이트**(`BINARY_STATE_BYTES`, 시제품 JSON은 약 85바이트).
- 서버는 방마다 10Hz로 **스냅샷 하나로 묶어** 각 사람에게 보냅니다(사람 수만큼 따로 보내지 않음).
- 방 최대 20명(한 방 안에서만 서로 보임). 클라이언트는 이미 상한 60명까지 받도록 되어 있고, 보이는 건 가까운 순입니다.
- 사람당 받는 양 ≈ (N−1)×16B×10Hz + 포장 ≈ **약 3.4KB/s(방 20명)**. 24시간 평균 동시접속 1명 유지 시 **월 약 9GB**. 같은 계산으로 평균 동시접속(CCU) 10명(방 1개)은 월 약 47GB, 100명 약 0.9TB, 500명 약 4.5TB, 2,000명 약 18TB입니다.
- 아래 비용은 **"그 CCU를 한 달 내내 유지"하는 상한**입니다. 실제로는 사람이 없으면 비용이 줄어듭니다. 단가는 2026-11 검색 결과이고 **계약 전 재확인**이 필요합니다.

### 방식별 비교
| | A. 직접 만든 WebSocket 서버 | B. 서버리스 방(Cloudflare Durable Objects 등) | C. 관리형 pub/sub(Ably 등) | D. WebRTC P2P |
|---|---|---|---|---|
| 구조 | Node 서버 1~N대, 방=메모리 객체 | 방마다 객체 1개, 접속은 엣지 | 채널에 발행·구독 | 브라우저끼리 직접. 서버는 연결 중개만 |
| 월 비용 CCU 10 / 100 / 500 / 2,000 | €4~9 / €4~9 / €9~15 / €15~30 (유럽 VPS, 20TB 포함) | ≈$7 / $40 / $200 / $800 | **수천 달러 이상**(아래 설명) | 서버비 거의 0, 중개 서버 월 €4~ |
| 운영 부담 | 높음: 배포·모니터링·재시작을 직접 | 낮음: 서버 관리 없음 | 가장 낮음 | 낮음(그러나 아래 위험) |
| 한국 지연 | 서버 위치에 달림(유럽 ~250ms+, 싱가포르·도쿄·서울은 더 가까움) | 엣지에서 접속, 방 객체가 한 곳에 고정 | 가까운 리전 선택 | 직접 연결이라 가장 빠를 수 있음 |
| 악용 대응 | 서버에서 직접 검증·차단 가능 | 같음 | 서비스 기능 범위 안에서만 | **어려움**: 서버가 위치를 못 보고, 상대 IP가 노출 |
| 종속성 | 낮음 | 중간(그 회사 API) | 높음 | 낮음 |

**근거와 가정**
- Cloudflare Durable Objects: 받는 WebSocket 메시지 20개가 요청 1건, 보내는 메시지는 무료, 요청 100만 건당 $0.15, 사용 시간 100만 GB-s당 $12.50(월 100만 요청·40만 GB-s 포함) — [공식 가격 문서](https://developers.cloudflare.com/durable-objects/platform/pricing). 계산은 "방 1개가 연결을 안 끊고 24시간 켜진 상태(128MB)"로 했습니다. CCU 2,000이면 요청비 약 $395 + 사용 시간비 약 $410입니다. 위치를 5Hz로 줄이면 요청비는 절반입니다.
- Hetzner: 독일·핀란드 서버는 월 20TB 트래픽이 포함, 최소 요금은 월 €4~9 수준이나 자료마다 값이 달라 대략값입니다. 미국·싱가포르는 포함 트래픽이 1~8TB로 줄어듭니다 — [검색 결과 요약](https://betterstack.com/community/guides/web-servers/hetzner-cloud-review/). 한국 사용자를 노리면 유럽 서버는 지연이 커서, 싱가포르(포함 트래픽 적음)나 트래픽 과금 방식(예: 대형 클라우드의 서울 리전, 기억상 GB당 약 $0.09, **미확인**)을 써야 합니다. 이 경우 500명 월 약 $400, 2,000명 약 $1,600이 됩니다.
- Ably: 메시지 100만 건당 $2.50(대량 할인 시 최저 $0.50), 기본 요금 월 $29 — [공식 가격](https://ably.com/pricing). 10Hz로 한 방 10명이면 발행·수신을 합쳐 초당 약 1,000건이라 **한 달 약 26억 건 = 약 $6,600**입니다. 위치 같은 고빈도 데이터에는 맞지 않아 후보에서 뺍니다(채팅·알림용에 적합).
- Colyseus Cloud·Photon 같은 게임 전용 관리형은 가격을 확인하지 못했습니다. 후속 조사 대상입니다.

**추천:** A(직접 WebSocket)를 1차로. 이유는 ① 비용 예측이 쉽고(고정 월 €10 안팎) ② 이름 검열·속도 제한·차단을 서버에서 한 곳에 둘 수 있고 ③ 시제품의 전송 계층 인터페이스(`send/onmessage/close`)가 그대로 맞기 때문입니다. 사람이 몰려 운영 부담이 커지면 B로 옮기기도 쉽습니다(방 = 객체 구조가 같음).

### 서버가 할 일(최소)
1. 접속 시 임시 ID 발급, 닉네임 검사(아래), 방 배정(한 방 20명).
2. 위치 메시지 속도 제한(초당 15회 초과 드롭), 이동 속도 검증(순간이동 거부: 단, 구간 이동 버튼은 허용 표시).
3. 방마다 10Hz 스냅샷 묶음 전송.
4. 신고 접수·저장, 제재 목록.
5. 서버가 안 해도 되는 것: 지형·충돌 계산. 클라이언트가 자기 위치만 알립니다(고도 y는 받는 쪽이 같은 지형으로 계산).

## ② 개인정보·닉네임·신고 처리안

### 수집·보관 (제안)
| 정보 | 용도 | 보관 |
|---|---|---|
| 닉네임(12자 이내, 선택) | 이름표 | 접속 동안만. 안 정하면 `등산객XXXX` |
| 임시 ID(접속마다 새로 발급) | 구분 | 접속 동안만 |
| 게임 안 좌표·방향 | 다른 사람에게 표시 | 저장하지 않음(메모리에서 즉시 폐기) |
| 접속 IP | 악용 차단(접속 수 제한·신고 숨김 유지) | **디스크·로그에 저장하지 않음.** 메모리에서 프로세스마다 바뀌는 비밀 값으로 만든 해시만 쓰고 서버가 꺼지면 사라짐(11-08 구현 기준, 처음 제안했던 "30일 보관"은 쓰지 않음) |
| 신고 기록(신고자 임시 ID, 대상 임시 ID·닉네임·시각·사유) | 제재 검토 | 90일(제안) |
- **계정·가입·이메일·실제 위치(GPS)·채팅 내용은 받지 않습니다.** 글자 채팅은 1차 범위 밖입니다. 위치는 가상의 게임 좌표뿐이라 실제 위치정보가 아닙니다.
- IP는 법적으로 개인정보에 해당할 수 있고, 만 14세 미만 이용 가능성이 있으므로 **서비스 공개 전 법무·개인정보 처리방침 확인이 필요합니다**(제가 법적 판단을 한 것이 아닙니다).

### 닉네임 (시제품에 구현됨: `sanitizeName`)
- 제어·방향 전환·보이지 않는 문자를 지우고, 공백을 정리하고, 12자로 자릅니다. 링크처럼 보이면 버리고 대체 이름을 씁니다. 금칙어 목록을 넘기면 걸러냅니다.
- 서버에서도 **같은 검사를 다시** 합니다(클라이언트는 믿지 않음). 금칙어 목록은 대표·운영 결정이 필요합니다.

### 신고·차단
- **차단(구현됨):** 목록에서 누르면 그 사람이 내 화면에서 사라지고 그 사람의 인사·셀카 요청을 받지 않습니다. 내 브라우저에 저장됩니다.
- **신고(시제품):** 신고하면 기록하고 동시에 차단합니다. 지금은 내 컴퓨터에만 저장합니다. 사유는 `부적절한 이름 / 방해·괴롭힘 / 기타`.
- **서버가 생기면:** 같은 기록을 서버로 보내고, 같은 사람이 서로 다른 3명 이상에게 신고되면 **자동으로 24시간 닉네임 숨김·방 재배정**(제안), 운영자가 검토해 해제·제재합니다. 확인 담당자와 처리 기한(예: 영업일 2일)은 대표 결정 사항입니다.
- 행동 남용 방지(구현됨): 인사·손 흔들기 3초, 같이 셀카 요청 15초 쿨다운, 요청 10초 만료, 거리 밖(6m) 요청 거부.

## ③ 내 컴퓨터 안 시제품

### 쓰는 법
`npm run dev` 후 같은 브라우저에서 창 2개를 엽니다.
```
http://127.0.0.1:5173/?multi=방이름&name=하늘&start=entrance
http://127.0.0.1:5173/?multi=방이름&name=바다&start=entrance
```
- 주소에 `multi`가 없으면 이 코드는 불러오지도 않습니다(기존 동작 불변). `multi` 모드에서는 창끼리 저장 파일을 덮어쓰지 않도록 자동 저장을 끕니다.
- 오른쪽 위 패널: 접속 인원, 가까운 사람, **인사(X) · 손 흔들기(G) · 같이 셀카(K) · 이름표 켜기/끄기(N)**, 목록(차단·신고). 휴대폰에서는 버튼을 누릅니다. 기존 키와 겹치지 않는 키만 썼습니다.

### 구성
| 파일 | 역할 |
|---|---|
| `src/multi-protocol.js` | 순수 로직: 메시지 규격, 이름 정리, 위치 보간, 거리별 표시 단계, 인사·셀카 상태기계, 차단·신고. 서버가 생겨도 그대로 씀 |
| `src/multi-transport.js` | 전송 인터페이스 `{send,onmessage,close}`. 지금은 BroadcastChannel과 가짜 방(지연·유실 조절) |
| `src/multi-client.js` | 화면 연결: 모델 풀, 이름표, 패널, 키, 같이 셀카 |
| `src/multi-gestures.js` | 손 흔들기·인사 자세(뼈를 월드 방향으로 덮어씀, 새 애니메이션 파일 없음) |
| `src/multi-sim.js` | 20명 흉내용 가짜 등산객 |
| `tests/multi-protocol.test.mjs` | 12개 |
| `scripts/verify-multi.mjs`, `scripts/measure-multi.mjs` | 두 창 확인, 부하 측정 |

`main.js`에는 5곳만 손댔습니다(멀티 모드일 때만 동작): 모듈 연결, 같이 셀카 중 걷기 정지, 걷는 아바타 뒤 자세 덮기, 프레임 갱신, 저장 끄기. `performance-metrics.js`는 단계 이름 `multi`를 한 개 추가했습니다.

### 지금 한계
- **동영상은 못 찍었습니다.** Playwright 영상 녹화에 필요한 ffmpeg가 설치돼 있지 않아 캡처로 대신했습니다.
- 같이 셀카에서 **파트너 화면**은 요청자를 바라보는 장면이 아니라 자기 시점 그대로입니다(설계상 개선 여지: 파트너에게 요청자 휴대폰 시점 보여 주기). 제3자는 둘의 셀카 자세를 보지 못합니다.
- 구역이 다른 사람끼리(광장↔산길)는 같은 거리 계산을 하지 않습니다(같은 구역일 때만 행동 가능).
- 걷기 길(route) 위에서 파트너를 옆자리로 옮길 때 몸 방향은 길 방향을 따릅니다. 광장·정상 구역에서는 요청자 방향을 따릅니다.
- 밤에는 모델로 그린 가까운 4명에게 헤드랜턴 빛이 없습니다(캡슐로 그리는 사람만 기존 밤 조명 장치 사용).
- 복장은 이름 해시로 4종 중 하나 자동 배정(내 복장을 전송하지 않음). 이름표 위치는 추정이며 셀카 화면(좌우 반전)에서는 이름표를 숨깁니다.
- 소리(인사 소리 등)는 없음.
- 실제 네트워크 지연·유실은 가짜 방으로만 흉내 냈습니다(실서버 미접속).

읽는 법
- **모델 1명 = draw call 약 60~75개, 삼각형 약 4.7만, multi CPU 약 0.6ms**입니다. 캡슐은 사람이 늘어도 draw call이 늘지 않습니다(밤 조명 장치의 묶음 그리기). 그래서 모델 상한이 성능을 결정합니다.
- 모델 4명 상한이면 20명이든 60명이든 비슷합니다. **상한 8명부터 p95가 33ms로 튀고, 전원 모델은 34fps**입니다.
- 지연 150ms·유실 10%에서도 보간이 끊김을 가려 줍니다(fps 영향 없음).
- 브라우저 메모리(JS 힙)는 약 1.6~2.0GB로 눈에 띄게 늘지 않았습니다.

한계: 헤드리스 크롬이고 60Hz에 걸려 있어 **60fps라고 나온 장면의 여유는 알 수 없습니다.** GPU 시간은 측정하지 못했고 CPU 단계 시간(render·multi)만 봤습니다. 실제 휴대폰·저사양 노트북은 확인하지 못했습니다. **모델 상한은 휴대폰에서 더 낮춰야 할 가능성이 큽니다**(예: 2명). 모델 1명당 draw call을 줄이는 방법(사람 메시 합치기·단순 LOD)은 후속 과제입니다.

## 대표 결정 요청
1. **서버 방식**: A 직접 WebSocket(추천) / B 서버리스 / 기타
2. **서버 지역**: 한국 사용자 위주면 서울·도쿄·싱가포르 중 어디(지연 ↔ 트래픽 비용)
3. **닉네임 정책**: 자유 입력 + 금칙어 필터(추천) / 정해진 목록에서 고르기
4. **신고 처리 담당·기한**, 자동 숨김 기준(서로 다른 3명 신고, 24시간)
5. **IP 디스크 미저장(메모리 해시만)·신고 90일 보관** 안 승인, 법무 확인 진행 여부
6. **한 방 최대 인원**(추천 20)과 화면에 모델로 그릴 인원(추천 4, 휴대폰 2)
