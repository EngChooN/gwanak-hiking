# 웹·모바일 웹 관악산 체험 엔진 기술 검토

작성: 산개발 · 2026-11-03 · 프로젝트 `/Users/joonyoung/gwanak-hiking`

## 권고

**현재 three.js r180 WebGLRenderer를 유지하고 보행·접지·청크 로딩 구조를 먼저 검증한다. WebGPURenderer는 별도 비교 실험 후보로 둔다. 지금 다른 엔진으로 전면 이전할 근거는 부족하다.**

대표 질문에 대한 답: HTML은 화면과 입력을 담는 껍데기이며, 이 앱의 3D는 WebGL을 통해 GPU에서 그린다. 다른 엔진도 웹으로 제공하면 브라우저의 CPU·GPU·메모리·발열 제약을 받는다. WebGPU는 명령 제출과 GPU 계산을 개선할 기회를 주지만, JavaScript에서 반복하는 발 접지 검색이나 한 프레임에 몰린 메시 생성을 자동으로 해결하지 않는다. 렌더러 교체만으로 현재 끊김이 사라진다고 보장할 수 없다. three.js는 WebGPU와 WebGL 2 백엔드를 제공하지만 렌더러별 성능 차이는 장면에 따라 달라질 수 있다고 설명한다. [three.js 렌더러 전환 안내](https://threejs.org/manual/pages/webgpurenderer)

**앞 단계에는 유효한 Chrome 프로파일 결과가 없다.** 명령 실행 거부로 전후 fps, 함수별 CPU 시간, GPU 시간, 모바일 측정이 미완료다. 아래의 현재 병목 평가는 코드에서 발견한 작업량에 근거한 잠정 판정이다. ‘프로파일로 엔진 문제가 아님을 증명했다’는 결론은 내리지 않는다.

## 대상과 증거 수준

- 목표: 실제 넓은 지형·대량 식생·서울 원경을 보며 자동 걷기. 웹과 모바일 웹 모두 제공.
- 확인한 프로젝트 기반: Vite, three.js r180, GLB/Meshopt, InstancedMesh/LOD, DEM 격자, 등산로 ribbon, 사용자 정의 GLSL, SSAO·그림자, DOM UI, Web Audio.
- 현행 코드 정보는 앞 단계에서 읽은 소스와 반영 내역을 사용했다. 이 보고서 작업에서는 `git status --short`로 기존 미커밋 변경의 존재를 재확인했다.
- 공식 문서는 작성일에 조회한 내용을 사용했다. three.js의 현행 문서가 r180의 모든 기능을 보장하는 것은 아니다. WebGPU 시험 시 버전을 고정하고 해당 버전에서 기능·회귀 검증을 한다.
- 아래의 크기·성능 경향 및 이전 공수는 기술적 추정이다. 엔진 6종을 동일 콘텐츠로 빌드하거나 실기기 벤치마크한 결과가 아니다.

## 첫 로딩 크기와 메모리

현재 6개 후보의 동일 장면 빌드가 없으므로 **정확한 MB 순위는 미측정**이다. 공개 데모의 압축된 엔진 파일과 전체 게임의 다운로드 크기를 섞어 비교하지 않는다. 표의 상대 경향은 런타임 구성에 따른 추정이며, 기능 제거·압축 설정에 따라 겹칠 수 있다.

| 선택지 | 초기 코드·로딩 구성 | 메모리 특성 | 현재 판단 |
|---|---|---|---|
| three.js WebGLRenderer | JS 모듈 + 선택한 loader/후처리. 기존 필요한 모듈만 포함 가능 | JS 힙·geometry·전개 텍스처·GPU 타깃·디코더 작업 버퍼 | 현 구성에서 추가 런타임 도입이 없다. 원경·숲을 모두 첫 화면 전에 준비하지 않는 것이 유리 |
| three.js WebGPURenderer | 새 렌더러·TSL·후처리 및 호환 경로의 실제 번들을 측정해야 함 | 위 항목 + 파이프라인·바인딩 캐시, 자산을 두 렌더러에 중복 올리면 증가 | 전환이 다운로드 감소를 의미하지 않는다. A/B 비교는 별도 페이지·순차 실행으로 중복 메모리를 피함 |
| Babylon.js | 필요한 모듈/loader만 번들링. 전체 배포 번들을 그대로 쓰면 불필요한 기능 포함 가능 | 장면 객체·상태 관리·GPU 자산. thin instance는 개별 객체 비용 축소 가능 | 기능 통합의 편의와 번들 크기를 함께 평가. [Thin Instances](https://doc.babylonjs.com/features/featuresDeepDive/mesh/copies/thinInstances) |
| PlayCanvas | Engine 모듈과 사용하는 시스템·자산 handler. 브라우저 JS 기반 | 엔티티 수·instance buffer·GPU 자산 관리 | 필요한 시스템만 등록하는 방식으로 불필요한 코드를 줄일 수 있다. [독립 엔진 구성](https://github.com/playcanvas/developer-site/blob/main/docs/user-manual/engine/standalone.md) |
| Unity WebGL | loader·framework JS·Wasm·시작 장면의 `.data`, 필요 시 AssetBundle | Wasm/Unity 힙 외에 전개된 `.data`·브라우저·GPU 메모리도 존재 | 시작 데이터와 힙 피크 관리가 중요. AssetBundle로 다운로드·해제 시점을 분리. [Unity 메모리](https://docs.unity.com/en-us/engine/6000.0/manual/platform-specific/webgl/develop/memory) |
| Godot 4 웹 | JS·Wasm·프로젝트 자산 패키지 | 엔진 런타임·자산·GPU 메모리. 커스텀 템플릿으로 미사용 기능 제거 가능 | JS 렌더러만 바꾸는 경우보다 초기 구성 부담이 커질 가능성. 정확한 차이는 최적화된 export로 측정. [웹 크기 최적화 안내](https://raw.githubusercontent.com/godotengine/godot-docs/stable/tutorials/export/exporting_for_web.rst) |

모든 엔진에서 2048² RGBA8 비압축 텍스처 한 장은 mip 포함 약 21.3MiB다(`2048×2048×4×4/3`). 다운로드 JPEG가 작아도 GPU 메모리는 별개다. PBR 3장 세트라면 약 64MiB이므로, 숲 4종을 가져오는 것만으로도 쉽게 예산이 커진다. KTX2/Basis 등 GPU 압축은 대상 기기의 실제 전개 포맷까지 확인해야 한다. `renderer.info.memory.textures`는 개수이며 바이트가 아니다.

첫 로딩은 ①빈 실행기 압축 전송 바이트 ②최초 보행 가능 시점까지의 총 바이트 ③최초 보행 시간 ④다운로드·디코딩·GPU 업로드 중 메모리 피크 ⑤10분 후 상주 메모리로 따로 기록한다. 동일한 지형·나무·뷰포트·빛·후처리를 쓰고 Brotli/gzip 조건을 맞춘다. 기존 앱의 전체 로딩 크기도 아직 실측되지 않았다.

[MultiMesh 제약](https://docs.godotengine.org/en/4.4/tutorials/performance/using_multimesh.html), [공식 웹 데모 제한](https://godotengine.github.io/godot-demo-projects/) |

PlayCanvas의 기본 인스턴싱은 개별 인스턴스별 frustum culling을 하지 않는다고 명시한다. Godot MultiMesh도 묶음 전체의 가시성 판단을 사용한다. 따라서 엔진 이름과 무관하게 ‘13만 그루를 하나의 거대한 묶음으로 만들기’보다 수종·공간 청크별 묶음이 필요하다. 산림은 잎의 투명 영역이 중첩되는 픽셀 비용도 커서, 드로우콜만 줄이고 실제 그리는 잎 면적을 유지하면 GPU 병목이 남을 수 있다. ## 현재 코드 재사용과 이전 비용

공수는 **개발자 1명, 현재와 비슷한 장면의 기능·화질 동등성 확인까지의 계획 추정**이다. 자료 조사·새 고해상도 풍경 제작·현장 검수는 제외한다. 일정 약속이나 벤치마크 결과가 아니다.

| 선택지 | 그대로 쓰기 쉬운 부분 | 다시 연결하거나 작성할 부분 | 상대 비용 / 계획 범위 |

## 앞 단계 결과로 내릴 수 있는 판정

| 증거 | 확인 상태 | 판정 가능한 범위 |
|---|---|---|
| W/S·자동 걷기에서만 크게 저하 | 대표 관찰, 방향별 동일 구간 계측 없음 | 보행 위상·경로 진척에 묶인 작업을 우선 조사할 단서 |
| 접지 높이 조회마다 경로 검색·등산로 raycast 반복 | 수정 전 코드에서 확인 | 비용이 큰 알고리즘 구조. 엔진 교체 없이 공간 색인으로 줄일 수 있음 |
| 경계 진입 시 여러 지형 청크 동기 생성 | 수정 전 코드에서 확인 | 생성·업로드를 분산할 대상. 실제 spike 기여도는 미측정 |
| 3인칭 충돌 전 숲 전체 월드 행렬 강제 갱신 | 수정 전 코드에서 확인 | 불필요한 전체 scene 갱신을 줄일 후보. 실제 CPU 시간은 미측정 |
| 이미 나무 인스턴싱·GLB 캐시 사용 | 코드에서 확인 | ‘나무 수만큼 개별 drawcall’이라는 가정은 부정확. 재질·LOD·알파 오버드로·그림자는 따로 확인 |
| 수정 전후 fps·p95·50ms 초과·GPU 시간 | **미측정** | 주원인 비중, 개선 폭, 엔진 한계, 55/30fps 합격 여부 확정 불가 |

**잠정 판정: 콘텐츠 처리 구조와 CPU 작업 배치를 먼저 해결하는 것이 합리적이다. 엔진 한계로 판정할 증거는 아직 없다.** 엔진 문제가 없다고 확정한 것도 아니다. 변경 후에도 CPU 렌더 제출 시간이 지배적이면 WebGPU/타 엔진의 이득을 비교하고, 픽셀 비용이 지배적이면 해상도·잎 오버드로·후처리·그림자와 LOD를 우선 조정한다. 이전해도 같은 지형·식생 예산은 필요하다.

## 다음 검증과 전환 기준

1. 기존 `scripts/benchmark-performance.mjs`와 수정 전 소스 보존 서버로 Chrome 추적·CPU profile·프레임 표를 만든다. `window.__hikingMetrics.performance`에서 단계별 CPU 시간과 호출량을 기록한다. `lighting.render`의 CPU 소요를 GPU 실행 시간으로 해석하지 않는다.
2. 같은 위치·뷰포트·DPR에서 접지, 지형 갱신, 카메라 충돌, SSAO, 그림자를 각각 끈 통제 실험을 한다. 움직임·실제 이동 거리를 기록한다. A/D는 길 폭 끝에 도달하면 멈추므로 정지 상태와 걷기를 섞지 않는다. 64m 경계 통과도 별도 추적한다.
3. 높은 화질 M 시리즈 Mac Chrome 평균 55fps 이상, CPU 4배 균형 30fps 이상을 검증한다. 50ms 초과 비율 1% 이하는 앞 단계에서 정한 임시 기준이며 반복 경계 끊김은 별도 결함으로 기록한다. CPU 4배 감속은 모바일 GPU·메모리·발열의 대체 검증이 아니다.
4. 모바일은 Safari 26 계열과 실제 지원할 이전 iOS의 WebGL 경로, Android Chrome 중급/상급 기기를 포함한다. 기기·OS·브라우저·GPU·전원·화질을 기록하고, cold load와 cache load, 10분 자동 걷기, 백그라운드 복귀·컨텍스트 손실을 확인한다. 모바일 목표는 우선 균형 지속 30fps로 **제안**하며 기획 확정값과 구분한다.
5. WebGPU POC는 같은 자산·시점·색감·LOD·그림자를 사용해 별도 페이지에서 비교한다. 최신 엔진만 화질을 낮춘 비교는 하지 않는다. GPU 시간 측정 API는 지원 시 사용하고 지원하지 않으면 해상도/패스 통제 실험과 프레임 시간으로 판단한다.

전환 의사결정의 제안 기준: 구조 개선 후에도 렌더 제출 CPU가 지배적인 미달 상태이고, WebGPU POC가 목표 기기에서 p95 프레임 시간을 20% 이상 줄이며 초기 로딩·메모리 피크 증가가 10% 이내이고 WebGL fallback 화질·기능을 유지하면 전환을 검토한다. 이 20%/10%는 제품 요구가 아니라 이전 비용을 정당화하기 위한 **제안 문턱**이다. 기존 WebGL이 목표를 만족하면 출시 경로를 유지한다. Babylon/PlayCanvas는 같은 구간의 작은 비교 구현에서 기능 생산성까지 유리함이 확인될 때 검토한다. Unity/Godot는 네이티브 앱 병행이나 저작 도구 중심의 제작 방식 변경이 별도 목표가 될 때 재검토한다.

산풍경에게 전달한 임시 예산(모든 패스 합계: 높음 삼각형 250만·drawcall 800·자산 텍스처 256MiB, 균형 150만·500·192MiB)은 엔진별 성능 점수가 아니다. 새 고해상도 지형·숲을 통합한 뒤 실제 프레임·메모리 기준으로 확정한다. 상세는 [성능 측정과 렌더링 예산](./성능-측정과-렌더링-예산.md)을 참조한다.

## 가정

- 웹·모바일 웹 제공을 유지하며 네이티브 앱 전환은 이번 권고 범위에 넣지 않는다.
- ‘실제 관악산 풍경’은 동일 자료·비슷한 화질로 비교해야 한다. 저품질 대체물을 더 빠른 엔진의 근거로 삼지 않는다.
- 앞 단계 프로파일이 없으므로 성능 판정은 잠정이다. 가짜 fps·정확하지 않은 다운로드 MB·고정 공수를 실측값처럼 기입하지 않는다.
- 이번 작업은 문서 작성이다. 기존 성능 코드·화질 토글을 수정하거나 외부 엔진·유료 자료를 설치하지 않는다.

## 대표 확인 필요

보고서 작성과 공식 문서 조사는 완료했다. 앞 단계에서 막힌 실행 검증을 이어가려면 아래 명령이 남아 있다. 삭제·배포·push·추가 외부 전송은 하지 않았다. 엔진 구매·가입도 하지 않았다.

```sh
cd /Users/joonyoung/gwanak-hiking
nvm use 24
# 기준 서버, 별도 터미널에서 before 측정 후 종료
node scripts/performance-server.mjs before
LABEL=before HEADED=1 node scripts/benchmark-performance.mjs
# 현재 코드 서버, 별도 터미널에서 after 측정
npm run dev -- --port 5176
LABEL=after HEADED=1 node scripts/benchmark-performance.mjs
node scripts/compare-performance.mjs
npm test
npm run build
# 이 보고서만 따로 커밋할 경우
git add -- docs/엔진-기술검토.md
git commit -m 'docs: compare web 3D engines for Gwanak hiking'
```

이번 문서는 실행 코드 변경이 없어 새로운 실행 테스트를 만들지 않았다. 기존 성능 변경의 테스트 통과 상태는 여전히 미확인이다. 최종 확인에서 `git status --short`는 성공했고 새 문서의 존재를 확인했다. 아래 문서 공백 검사와 위 `git add`는 모두 `rejected by user`로 거부되었다. 따라서 문서는 미추적 상태로 저장되었으며 커밋하지 못했다. `git add`가 실패하여 `git commit`은 실행하지 않았다.

```sh
git diff --no-index --check /dev/null docs/엔진-기술검토.md
```
