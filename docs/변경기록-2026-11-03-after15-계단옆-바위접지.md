# after15 — 계단 옆 바위 높이와 접촉 측정 영역 보정

산개발 / 2026-11-03. 구현 제출, 실행 검수 대기.

## 원인과 수정

12차 자료의 바위 접촉 계산 groundY=275.21m와 화면 지형 약 274.48m 사이 불일치를 코드에서 확인했다. `floorHeight`는 연속 높이 함수다. 실제 근경은 이 함수로 만든 2m 격자를 삼각형으로 연결한 뒤 `stairTerrainClearance`로 계단 회랑과 겹치는 꼭짓점을 추가로 낮춘다. 기존 바위 배치와 contactProbes는 이 마지막 보정을 반영하지 않았다. 따라서 바위는 높은 곳에 남고 같은 XZ의 낮은 지형에 그늘이 표시될 수 있었다.

- `assets/realistic/load-landscape.js`: 실제 근경과 같은 64m 청크 원점·2m 격자·Float32 삼각형·계단 회랑 보정을 이용하는 바위 전용 높이 조회를 추가했다. 아직 스트리밍되지 않은 청크도 같은 기준으로 조회한다. 조회용 임시 메시를 장면에 추가하지 않고 형상을 해제하며, 삼각형 숫자 색인은 최대 8청크만 보관한다.
- 길가 상세 바위 전체와 계단 인근 일반 바위(가장 가까운 구간이 계단이고 거리≤노폭/2+8m+음영반경)를 최종 2m 지형 높이에 맞춘다. 계단 밖 길가 바위도 연속 함수와 삼각형 보간의 차이를 보정해 화면 측정 기준을 일치시킨다. 일반 바위의 먼 사면 배치는 유지한다.
- `seatContactInstance`는 첫 LOD의 변환된 밑부분 바닥과 보정된 지형의 높이 차이를 구해 **모든 LOD의 실제 인스턴스 행렬**에 같은 Y 이동을 적용한다. XZ·회전·크기·음영 반경·차폐율은 유지한다. 높이를 옮긴 뒤 실제 Float32 행렬에서 접촉점을 다시 읽고, 메시 경계 상자·구를 갱신한 뒤 기존 정적 카링에 등록한다. `heightCorrection`과 `terrainAligned`로 추적한다.
- 계단 형상·회랑 보정 알고리즘·노면·발 접지 계산을 바꾸지 않았다. 음영 스탬프 XZ가 같아도 바위 몸체가 화면 지면에 내려오므로 빈 바닥의 떨어진 그늘을 없애는 접근이다. 실제 시각 결과는 새 캡처로 확인해야 한다.

## 높이 측정

`hiking.contactProbes()`는 바위 XZ에서 현재 지형 메시들에 수직 광선을 쏴 `renderedGroundY`와 `groundError=|바위 밑부분 바닥−렌더 지형|`를 기록한다. `analyticGroundY`도 남겨 이전 연속 함수와의 차이를 대조한다. 접촉점의 화면 투영은 렌더 지형 기준으로 수정했다. 누락 시 groundError는 null이며 높이 0으로 간주하지 않는다. 35m 내 후보의 기존 128개 제한을 캡처 진단에서 제거했다.

계단 캡처 JSON의 `contacts.first/third.rockGrounding`에 다음을 기록한다.

- `visibleRendered`: 카메라 35m 안 visible·inFrame 바위 전체의 현재 렌더 지형 오차 최대·평균·개수·누락 수·개별 rows. 오차>0.05m 또는 누락은 캡처 errors에 추가한다. visible은 조상 표시 상태이며 다른 물체의 가림 판정은 아니다.
- `allStairSections`: 로드된 전체 배치에서 가장 가까운 경로 구간이 계단인 보정 대상 바위를 모두 측정한다. 최종 2m 회랑 보정 삼각형과 실제 첫 LOD 바닥의 오차 최대·평균·개별 rows다. 대상 0개·누락·0.05m 초과는 오류다. **화면 밖에는 현재 렌더 청크가 없을 수 있어 이 항목은 기준 삼각형 조회이며 실제 전 구간 화면 검수를 대체하지 않는다.** 현재 화면의 기저 지형 LOD 중첩 차이는 visibleRendered가 별도로 검출한다.

밑부분 상자의 최하단을 바위 바닥으로 정의한다. 경사진 바위의 전체 접촉 면적과 모든 꼭짓점의 지형 관통을 검사하는 지표는 아니다. 현재 길가 rock_09는 yaw·균일 배율 배치다. 다른 모델의 LOD별 바닥 형상 차이는 별도 검수가 필요하다.

## 측정 칸 보정

- 바위의 첫 LOD 전체 메시 경계 상자를 실제 배치 행렬로 변환해 `worldBounds`를 저장하고, 캡처 때 8꼭짓점을 투영해 `screenBounds`를 구한다.
- 기존 48×24px 대신 12차 `ring.mjs`의 거리 배율 `s=4.5/max(1,거리)`와 접촉점 기준 좌우 90s·위 30s·아래 70s를 사용한다. 여기에 투영된 바위 외접 상자의 좌우 12s·아래 32s 여유까지 포함하도록 넓힌다. 이미지 경계에서는 잘라낸다.
- `roadsideRockContactRegions[].bodyBounds`로 몸체 외곽 근사도 남긴다. 영역은 앞쪽 바닥을 포함하지만 몸체·옆 나무·UI 화소를 완전히 제외하지 않는다. 음영 끔/켬 비교와 원본 화면을 함께 판단해야 한다. 12차 도구는 RGB 산술평균이고 현재 지표는 기존 휘도 가중평균이므로 수치가 정확히 같지는 않다.
- `nearVisibleLarge` 요약은 넓힌 영역으로 계산한다. 15m 이내·b≥0.30m 후보를 먼저 선택해 24개 제한 때문에 합격 대상이 밀리지 않게 했다. 크기별 요약·길 가장자리 지표를 유지한다.

## 50.6ms 프레임 의견

12차 `performance-after14/results.json` 균형 4x에서 벤치 별도 rAF 최대는 50.6ms·50ms 초과 1회, p99는 34.8ms다. 같은 실행의 앱 내부 `metrics.performance.maxMs`는 35.4ms, 초과 0회이며 재컴파일은 0이다. 이는 서로 다른 rAF 계측의 표본 차이가 있다는 근거이며, 원인이 GPU 텍스처라고 확정하는 근거는 아니다.

접촉 지도는 초기 배치 완료 때 생성·업로드하고 프레임별 갱신하지 않는다. 벤치는 natureReady 이후 15초 이상 준비한 뒤 측정하므로 최초 38.9MB 업로드가 이 한 프레임을 직접 막았을 가능성은 낮다. 다만 지도 크기 증가로 GPU 메모리·캐시 부담이 늘 수 있으므로 간접 영향은 배제할 수 없다. CPU 4배 제한·스케줄링·카링/청크 처리·GC 등도 후보이며 새 실험 없이 원인을 단정하지 않는다. CPU trace만으로 GPU 지연을 분리할 수도 없다.

12차 지도의 실제 높이는 8193으로 선언 상한 8192를 넘었다. 나눗셈의 부동소수점 오차를 ceil할 때 생기는 문제라 크기 계산 결과를 resolutionLimit로 다시 제한했다. 현재 장치에서 오류가 없었으므로 이것을 50.6ms 원인으로 단정하지 않는다. after15 지도는 약 38.9MB를 유지하며 추가 GPU 패스·샘플·프레임별 갱신은 없다. 바위 접지 조회·경계 계산은 초기 로딩 비용이고, 광선·전체 계단 진단은 캡처에서만 호출한다.

## 검증 상태와 가정

`git diff --check` 통과. 다중 LOD가 같은 양만큼 내려가고 실제 행렬의 바닥이 목표 높이에 맞으며 XZ·차폐율이 유지되는 회귀 테스트를 추가했다. 테스트 본문·빌드·캡처·벤치는 실행하지 않았다. 새 결과 화면은 없으며 이전 화면을 after15 결과로 첨부하지 않는다.

가정: 기존 CC0 임시 배치와 밑부분 형상 근사다. 최종 2m 삼각형 높이로 몸체를 내리면 떨어진 그늘이 붙을 것으로 가정한다. 기저 지형 LOD와 근경 삼각형이 겹치는 곳, 경사진 밑면, 다른 LOD 형상은 실제 렌더 오차와 원본 화면으로 재확인해야 한다. 이번 수정은 결과 합격을 주장하지 않는다.
