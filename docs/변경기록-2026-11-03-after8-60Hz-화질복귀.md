# after8 — 60Hz 화질 복귀·AO 유지 판정

산개발 / 2026-11-03. 구현·정적 검사 완료, 실행 검수 대기. 커밋·push·삭제 없음.

## 수정

after7의 `mean<15ms` 복귀 조건은 60Hz 수직 동기 환경에서 달성할 수 없었다. 이번에는 두 시간을 구분한다.

- 실제 속도: 기존 rAF 간격 평균. 높음 목표 55fps(18.18ms)를 유지한다. 평균이 목표의 105%(19.09ms)를 초과하는 2초 창이 연속 2회이면 한 단계 내린다. 단발 계측 정지로 연쇄 하향하는 것을 줄이며, 성능 결과에서 느린 프레임을 제거하지 않는다.
- 복귀 여유: `main.js`의 frame 진입 시점부터 입력·이동·지형·렌더 제출·UI·저장·주기 통계 갱신이 끝날 때까지의 `performance.now()` 차이다. 브라우저의 다음 rAF까지 수직 동기 대기 시간은 포함하지 않는다. 프레임 간격 평균 ≤17.45ms(목표의 96%)이고 CPU 작업 평균 <12.73ms(목표의 70%)인 창이 3회 이어지면 한 단계 올린다. 따라서 60Hz·CPU 5ms인 경우 약 6초마다 복귀할 수 있다.

CPU 시간은 GPU 완료 시간이 아니다. CPU만 가볍고 GPU 병목으로 실제 간격이 느리면 복귀하지 않는다. GPU 시간 질의나 동기 GPU 대기는 도입하지 않았다. CPU 여유로 GPU의 AO 추가 비용까지 예측할 수는 없으므로 복귀는 시험이며, 실제 간격을 계속 감시한다.

복귀 후 12초 이내에 같은 단계에서 다시 하향하면 실패한 경계로 기록한다. 그 경계의 다음 복귀는 30초 대기 후 안정 창 3회를 다시 요구한다. 같은 경계가 반복 실패하면 대기는 60초, 최대 120초로 늘어난다. 느린 상태의 하향은 잠그지 않는다. 따라서 AO가 성능 예산을 넘는 장면에서는 6~10초마다 켜졌다 꺼지는 반복을 막고, 장면 부하가 줄면 나중에 다시 시험할 수 있다. 수동 상한 변경 시 이 이력은 초기화한다.

after7의 로딩 전 준비·보행 중 재컴파일 제거 구조는 유지했다. 복귀는 기존 resize 경로만 사용한다.

## 이 컴퓨터의 정상 단계 기준과 근거

**높음 조건 종료 기준은 step 0~2, AO true다. 기존 자료로 직접 뒷받침되는 기준 단계는 2다.** step 0 또는 1로 종료해도 동일한 성능·AO 유지 기준을 충족하면 정상이며, step 2를 강제로 고정하지 않는다. 정확히 어느 단계가 유지되는지는 새 실행으로 확인해야 한다.

근거는 after6 사본 `/private/tmp/gwanak-after6-review.CBU8qs/artifacts/performance-after6-culling-measurement/results.json`이다.

- 높음 W의 step 2·AO true에서 앱 평균 59.949fps, 최대 프레임 32.7ms였다. CPU stage 평균은 movement 0.018 + ambient 0.010 + hiker 0.088 + contact 0.444 + camera 0.043 + terrain 1.132 + render 4.106 ≈5.84ms다. 이번에 측정하는 전체 CPU 작업 시간과 동일한 지표는 아니지만, 기존 렌더·이동 작업에는 복귀 여유가 있다는 근거다.
- 높음 D도 step 2·AO true에서 약 60fps였다. after6 정지·S·자동·1인칭 W의 0.5초 정지는 셰이더 재컴파일로 확인됐으며, after7에서 제거됐다.
- after7의 step 4·AO false에서 59.9~60fps라는 수치는 AO 필요성을 판단하는 근거가 될 수 없다. 이번에는 AO 상태를 실제 측정 구간 전체에서 검증한다.

즉 현재 자료에는 이 컴퓨터에서 높음의 AO를 상시 꺼야 한다는 근거가 없다. 새 검수에서 step 3~4라면 정상으로 처리하지 않는다. `adaptive.transitions`에서 step 2의 `meanMs`가 19.09ms를 초과하는 연속 창으로 하향됐는지 확인하고, 원본 fps·최대 프레임·trace와 함께 판단한다. CPU 여유가 있는데 AO를 켠 상태에서만 실제 속도가 지속적으로 느리면 GPU 등 추가 분석이 필요하다. 새 수치 없이 성능 부족이라고 단정하지 않는다.

## 벤치마크 기록·판정

`hiking.adaptive()`는 갱신 주기를 기다리지 않는 현재 상태와 누적 카운터를 제공한다. benchmark의 측정 시작 rAF와 종료 콜백에서 직접 읽는다. 각 run의 results.json에 다음을 추가했다.

| 필드 | 의미 |
|---|---|
| adaptive.start / end | 시작·끝 step, ao, dpr, 누적 변경·프레임 수, 마지막 창의 meanMs / workMeanMs |
| adaptive.stepChanges | 구간 안의 누적 단계 변경 횟수 차이. 같은 단계로 돌아온 왕복도 누락하지 않음 |
| adaptive.transitions | 구간 안의 변경 시각(활성 누적 ms), from/to, 사유, 해당 창의 간격·CPU 평균 |
| adaptive.activeFrames / aoFrames / aoFrameRatio | 측정한 앱 프레임 수·AO가 켜진 프레임 수·비율 |
| compile.start / end / changes | 측정 시작·끝 준비 횟수와 증감 |
| aoPass | 높음은 시작·끝 AO true이고 전체 측정 앱 프레임에서 AO가 켜져 있어야 통과 |
| compilePass | 시작 compileCount 1, 측정 중 증감 0이어야 통과 |

모든 조건의 pass에 aoPass·compilePass를 결합했다. 기존 fps·최대 500ms·삼각형·도시 예산·측정 길이 판정은 그대로다. 단계 변경 이력은 최근 64개를 보관하며, 변경 횟수는 누적 카운터 차이로 기록한다. 20초 측정에서 최소 변경 간격이 약 4초여서 이력 누락은 없다. 측정 프레임의 제외·선별·정지 시간 숨김은 추가하지 않았다.

## 테스트·정적 검사

- `tests/adaptive-quality.test.mjs`: 60Hz·CPU 여유에서 4→2→0 복귀 및 안정 유지, AO 경계 실패 후 재시도 지연과 부하 개선 후 복귀, 지속 AO 병목의 반복 시험 제한, GPU 등 실제 속도가 느리거나 CPU 여유가 없을 때 복귀 금지, 목표 경계 흔들림·단발 정지, 단계·AO 프레임 카운터 보존 등 6개 테스트 추가. 기존 상한·하향 테스트도 연속 창 조건에 맞게 수정했다.
- after7의 15ms 미만 복귀를 강제하던 테스트 1개를 제거하고 위 60Hz 동작 테스트로 대체했다. 컴파일 경로 회귀 테스트에는 실제 CPU 시간 전달 연결도 확인하도록 추가했다.
- 변경 파일 5개(`src/main.js`, `src/adaptive-quality.js`, `scripts/benchmark-performance.mjs`, 테스트 2개)의 Node v22.23.4 `--check` 구문 검사 통과. 파일 본문을 실행하지 않는 구문 검사만 수행했다.
- `git diff --check` 통과. 단위 테스트·빌드·캡처·벤치마크는 미실행이며 새 fps·단계·AO 비율·접지 결과는 없다. 이번 테스트의 실행 통과 여부는 미확인이다.
